# Отчёты о результатах

Команды, которые что-то проверяют или прогоняют, умеют выгружать результат в файл для CI: `validate syntax-check`, `validate edt`, `test xunit`, `test yaxunit`, `test vanessa`. Настраивается это везде одинаково — одной парой опций:

| Опция | Переменная окружения | Описание |
|-------|---------------------|----------|
| `--report-format` | - | Формат отчёта. Опция повторяемая: несколько форматов за один прогон |
| `--report-path` | `VRUNNER_REPORT_PATH` | Куда выгрузить отчёт |

Если ни одна из них не задана, отчёт не формируется (кроме `test yaxunit`, где отчёт всегда пишется во временный файл ради саммари в консоли).

## Как разрешается путь

**Один формат** — `--report-path` берётся как есть. Вы сами решаете, файл это или каталог: для `junit` нужен файл, для `allure` — каталог.

```bash
vrunner validate syntax-check --report-format junit --report-path ./build/syntax.xml
```

**Несколько форматов** — в один файл они не помещаются, поэтому `--report-path` становится каталогом, а имена внутри берутся по соглашению:

```bash
vrunner validate syntax-check \
  --report-format junit \
  --report-format allure \
  --report-path ./build/reports
# → ./build/reports/junit.xml
# → ./build/reports/allure/
```

Недостающие каталоги создаются автоматически, причём **до** начала проверки: она может идти минутами, и падение на записи отчёта в самом конце обесценило бы весь прогон.

Если формат не указан, а путь задан — подставляется формат команды по умолчанию (везде это `junit`).

## Форматы по командам

Форматы определяет тот, кто пишет отчёт, поэтому список у каждой команды свой:

| Команда | Форматы | Несколько за прогон | Отчёт пишет |
|---------|---------|--------------------|-------------|
| `validate syntax-check` | `junit`, `allure` | да | vrunner |
| `validate edt` | `junit`, `allure`, `edt` | да | vrunner + 1cedtcli |
| `test xunit` | `junit`, `allure`, `json`, `mxl`, `genericexecution` + имя генератора Vanessa-ADD | да | Vanessa-ADD |
| `test yaxunit` | `junit`, `json`, `allure` | **нет, ровно один** | YAxUnit |
| `test vanessa` | `junit`, `allure`, `cucumberjson` | да | Vanessa-ADD |

Регистр значения не важен: `junit`, `jUnit` и `JUNIT` — одно и то же. Исключение — имена генераторов Vanessa-ADD в `test xunit`: они регистрозависимы и передаются как написаны.

Имена по умолчанию внутри `--report-path`, когда форматов несколько:

| Формат | Имя |
|--------|-----|
| `junit` | `junit.xml` |
| `allure` | `allure/` (каталог) |
| `json` | `report.json` |
| `mxl` | `report.mxl` |
| `genericexecution` | `generic.xml` |
| `cucumberjson` | `cucumber/` (каталог) |
| `edt` | `edt-validate.tsv` |

У `test vanessa` все форматы выгружаются в каталоги, поэтому имена там — `junit/`, `allure/`, `cucumber/`.

## Особенности отдельных команд

**`validate edt`** знает формат `edt` — это сырой файл результатов, который пишет сам `1cedtcli validate`: текст, по замечанию на строку, поля через табуляцию. Его принимает, например, [edt-ripper](https://github.com/silverbulleters/edt-ripper) для конвертации во внешние замечания SonarQube. Файл создаётся при любом прогоне (без запроса — во временном каталоге), а формат `edt` просто оставляет его по указанному пути.

**`test yaxunit`** формирует один отчёт за прогон — так устроен `reportFormat` в `yaxunit.json`. Два формата сразу приведут к явной ошибке, а не к тихой потере одного из них.

**`test xunit`** принимает не только перечисленные алиасы, но и полное имя генератора Vanessa-ADD — включая генератор-плагин, которого нет в списке (`ГенераторОтчетаМойФормат`, `GenerateReportJUnitXML`). Если нужны разные пути для каждого генератора, остаётся устаревшая опция `--reportsxunit` со скобочным синтаксисом.

**`test vanessa`** — единственная команда, где отчёты настраиваются не ключами запуска: у `bddRunner.epf` их для отчётов нет, всё задаётся файлом настроек. Поэтому vrunner читает файл из `--vanessasettings`, накладывает на него каталоги отчётов и передаёт в 1С уже временную копию. Исходный файл настроек не изменяется, а опции командной строки **перекрывают** одноимённые настройки — иначе они были бы бесполезны, ведь `--vanessasettings` есть почти в каждом проекте.

**Результаты Allure не очищаются.** Allure штатно собирает отчёт из результатов нескольких прогонов, и разные проверки одной сборки могут писать в общий каталог. Если нужен чистый каталог на каждый прогон — чистите его средствами сборки (у `test xunit` для этого есть флаг `--clear-reports`).

## Устаревшие опции

До появления общей пары у каждой команды был свой набор опций. Они продолжают работать и выводят предупреждение с подсказкой, чем их заменить:

| Устаревшая опция | Команда | Замена |
|------------------|---------|--------|
| `--junitpath <файл>` | `validate syntax-check`, `validate edt` | `--report-format junit --report-path <файл>` |
| `--allure-results <каталог>` | `validate syntax-check`, `validate edt` | `--report-format allure --report-path <каталог>` |
| `--reportsxunit "junit{путь}"` | `test xunit` | `--report-format junit --report-path <путь>` |
| `--reportxunit <каталог>` | `test xunit` | `--report-format junit --report-path <каталог>` |
| `--report <путь>` | `test yaxunit` | `--report-path <путь>` |
| `--report <файл>` | `validate edt` | `--report-format edt --report-path <файл>` |

Старые и новые опции можно держать вперемешку: они складываются, а при совпадении формата побеждает `--report-format`. Так отчёт, прописанный в файле настроек старым ключом, не теряется, когда в командную строку добавили новый.

Сбор покрытия тестами настраивается отдельно — это другой артефакт, а не отчёт о прогоне: [Сбор покрытия тестами →](./coverage)
